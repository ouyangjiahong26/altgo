# Architecture

## Overall Pipeline

altgo uses a linear pipeline architecture driven by keyboard events:

```
key listener → state machine → recording → ASR transcription → LLM polishing → clipboard + overlay + local transcription history (plain-text JSON)
```

**Transcription history**: only text is saved (the raw transcription `rawText` and the currently displayed `text`); recordings are never saved. The data file is `~/.config/altgo/history.json`. After a successful transcription (when `raw_text` is non-empty), a record is written and a `history-updated` event is broadcast so the history list on the main window's home page can refresh.

The key listener feeds key events into the main loop through an unbounded channel; the state machine returns commands synchronously, which are executed in place by `tokio::select!` branches, with a single-transcription mutex (see [ADR-0003](https://github.com/ouyangjiahong26/altgo/blob/master/docs/adr/0003-single-transcription-mutex.md) for details).

## Module Layout

Below is the Tauri core directory `src-tauri/src/` (excerpt):

```
src-tauri/src/
├── main.rs            # thin entry point, calls `lib::run()`
├── lib.rs             # Tauri assembly layer; managed state + pipeline thread
├── cmd.rs             # IPC commands: config, updates, pipeline, models, history...
├── config.rs          # TOML config loading (serde)
├── history.rs         # transcription history persistence (history.json)
├── state_machine.rs   # key state machine
├── audio.rs           # WAV encode/decode, thread-safe Buffer
├── transcriber.rs     # Transcriber trait
├── sherpa.rs          # local SenseVoice (embedded sherpa-onnx)
├── polisher.rs        # LLM text polishing
├── voice_pipeline/    # core pipeline (record → transcribe → polish → dispatch)
├── updater.rs         # app auto-update and manual checks
├── key_listener/      # key listening
│   ├── mod.rs         # shared trait + PlatformListener
│   ├── linux.rs       # xinput test-xi2 with evtest fallback; evtest preferred on Wayland sessions
│   └── windows.rs     # WH_KEYBOARD_LL low-level keyboard hook
├── recorder/          # audio recording
│   ├── mod.rs         # shared trait + PlatformRecorder
│   ├── linux.rs       # parecord (PulseAudio)
│   └── windows.rs     # cpal/WASAPI
└── output/            # result output (clipboard writes and text injection, no system notifications)
    ├── mod.rs         # shared trait + PlatformOutput
    ├── linux.rs       # xclip / xsel / wl-copy
    └── windows.rs     # arboard + SendInput
```

## Key State Machine

The state machine manages transitions between 5 states:

```
         press
  Idle ──────→ PotentialPress
   ↑               │
   │      long-press timeout   double-click timeout
   │               ↓               ↓
   │          Recording      WaitSecondClick
   │               │               │
   │         release           press again
   │               ↓               ↓
   └──────── ContinuousRecording ←─┘
```

- **Long press** (> 200ms) → enters `Recording`; release stops it
- **Double-click** (< 300ms interval) → enters `ContinuousRecording`; a single click stops it
- Uses `tokio::select!` to wait on key events and timeouts simultaneously

## Platform Strategy

**Linux**: CLI tools (`xinput`/`evtest`, `parecord`, `xclip`) are invoked as subprocesses, simplifying builds and dependency management.

**Windows**: native APIs are used — WH_KEYBOARD_LL keyboard hooks, cpal/WASAPI recording, and arboard clipboard plus SendInput text injection.

Platform modules expose unified traits (`KeyListener`, `Recorder`, `Output`), with per-platform implementations in each module's `linux.rs` / `windows.rs`; the pipeline consumes `Box<dyn Trait>` to stay decoupled from the platform.

## Transcription Engine

The only production implementation today is `SherpaTranscriber`: local SenseVoice with embedded sherpa-onnx, with the model kept resident in memory.

## Polishing Engine

- Supports 4 levels: `none` / `light` / `medium` / `heavy`
- Supports both the OpenAI-compatible chat API and the Anthropic Messages API
- Exponential backoff retries (up to 3 times)

From the history list on the home page, a single entry can be re-polished under the current polishing configuration based on its **`rawText`** (`polish_history_entry`).

## Frontend Routes (Main Window)

- React Router Hash mode: `/` home (status, latest transcription and the history list) and `/settings`.

## Testing Strategy

- `config.rs` / `audio.rs` / `history.rs` — comprehensive unit tests
- `sherpa.rs` — SenseVoice model presence and load-failure paths
- `polisher.rs` — mocks the OpenAI/Anthropic polishing APIs with `mockito`
- Platform modules — construction/smoke tests only
- Three CI jobs in total: Linux `amd64` and `arm64` both run `cargo test --lib`; the Windows job runs tests and builds the NSIS installer on x64, while arm64 only gets a cross-compilation check
