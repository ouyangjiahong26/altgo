# 架构设计

# Architecture

## 整体流水线

altgo 采用线性流水线架构，由键盘事件驱动：

```
按键监听 → 状态机 → 录音 → ASR 转写 → LLM 润色 → 剪贴板 + 悬浮窗 + 本地转写历史（纯文本 JSON）
```

**转写历史**：仅保存文本（原始转写 `rawText` 与当前展示 `text`），不保存录音；数据文件为 `~/.config/altgo/history.json`。转写成功后（以 `raw_text` 非空为准）写入一条记录并广播 `history-updated` 事件，供主窗口历史页刷新。

按键监听器经无界通道把按键事件送入主循环；状态机同步返回命令，由 `tokio::select!` 分支就地执行，单次转写互斥（详见 [ADR-0003](https://github.com/ouyangjiahong26/altgo/blob/master/docs/adr/0003-single-transcription-mutex.md)）。

## Overall Pipeline

altgo uses a linear pipeline architecture driven by keyboard events:

```
按键监听 → 状态机 → 录音 → ASR 转写 → LLM 润色 → 剪贴板 + 悬浮窗 + 本地转写历史（纯文本 JSON）
```

**Transcription history**: only text is saved (the raw transcription `rawText` and the currently displayed `text`); recordings are never saved. The data file is `~/.config/altgo/history.json`. After a successful transcription (when `raw_text` is non-empty), a record is written and a `history-updated` event is broadcast so the main window's history page can refresh.

The key listener feeds key events into the main loop through an unbounded channel; the state machine returns commands synchronously, which are executed in place by `tokio::select!` branches, with a single-transcription mutex (see [ADR-0003](https://github.com/ouyangjiahong26/altgo/blob/master/docs/adr/0003-single-transcription-mutex.md) for details).

## 按键状态机

状态机管理 5 个状态之间的转换：

```
         按下
  Idle ──────→ PotentialPress
   ↑               │
   │          长按超时         双击超时
   │               ↓               ↓
   │          Recording      WaitSecondClick
   │               │               │
   │          松开            再次按下
   │               ↓               ↓
   └──────── ContinuousRecording ←─┘
```

- **长按**（> 200ms）→ 进入 `Recording`，松开停止
- **双击**（< 300ms 间隔）→ 进入 `ContinuousRecording`，单击停止
- 使用 `tokio::select!` 同时等待按键事件和超时

## Key State Machine

The state machine manages transitions between 5 states:

```
         按下
  Idle ──────→ PotentialPress
   ↑               │
   │          长按超时         双击超时
   │               ↓               ↓
   │          Recording      WaitSecondClick
   │               │               │
   │          松开            再次按下
   │               ↓               ↓
   └──────── ContinuousRecording ←─┘
```

- **Long press** (> 200ms) → enters `Recording`; release stops it
- **Double-click** (< 300ms interval) → enters `ContinuousRecording`; a single click stops it
- Uses `tokio::select!` to wait on key events and timeouts simultaneously

## 平台策略

**Linux**：通过子进程调用 CLI 工具（`xinput`/`evtest`、`parecord`、`xclip`），简化构建和依赖管理。

**Windows**：走原生 API——WH_KEYBOARD_LL 键盘钩子、cpal/WASAPI 录音、arboard 剪贴板 + SendInput 文本注入。

平台模块暴露统一 trait（`KeyListener`、`Recorder`、`Output`），各平台实现在各自模块的 `linux.rs` / `windows.rs` 中，管道消费 `Box<dyn Trait>` 实现与平台解耦。

## Platform Strategy

**Linux**: CLI tools (`xinput`/`evtest`, `parecord`, `xclip`) are invoked as subprocesses, simplifying builds and dependency management.

**Windows**: native APIs are used — WH_KEYBOARD_LL keyboard hooks, cpal/WASAPI recording, and arboard clipboard plus SendInput text injection.

Platform modules expose unified traits (`KeyListener`, `Recorder`, `Output`), with per-platform implementations in each module's `linux.rs` / `windows.rs`; the pipeline consumes `Box<dyn Trait>` to stay decoupled from the platform.

## 转写引擎

当前唯一生产实现是 `SherpaTranscriber`：内嵌 sherpa-onnx 的本地 SenseVoice，模型常驻内存。

## Transcription Engine

The only production implementation today is `SherpaTranscriber`: local SenseVoice with embedded sherpa-onnx, with the model kept resident in memory.

## 润色引擎

- 支持 4 个级别：`none` / `light` / `medium` / `heavy`
- 支持 OpenAI 兼容 chat API 与 Anthropic Messages API
- 指数退避重试（最多 3 次）

历史页可对单条记录基于 **`rawText`** 再次调用当前润色配置（`polish_history_entry`）。

## Polishing Engine

- Supports 4 levels: `none` / `light` / `medium` / `heavy`
- Supports both the OpenAI-compatible chat API and the Anthropic Messages API
- Exponential backoff retries (up to 3 times)

From the history page, a single entry can be re-polished under the current polishing configuration based on its **`rawText`** (`polish_history_entry`).

## 前端路由（主窗口）

- React Router Hash 模式：`/` 首页、`/history` 历史、`/settings` 设置。

## Frontend Routes (Main Window)

- React Router Hash mode: `/` home, `/history` history, `/settings` settings.

## 测试策略

- `config.rs` / `audio.rs` / `history.rs` — 全面的单元测试
- `sherpa.rs` — SenseVoice 模型存在性与加载失败路径
- `polisher.rs` — 使用 `mockito` 模拟 OpenAI/Anthropic 润色 API
- 平台模块 — 仅构造/冒烟测试
- CI 共三个 job：Linux `amd64` 与 `arm64` 都跑 `cargo test --lib`；Windows job 在 x64 上跑测试并构建 NSIS 安装包，arm64 仅交叉编译检查

## Testing Strategy

- `config.rs` / `audio.rs` / `history.rs` — comprehensive unit tests
- `sherpa.rs` — SenseVoice model presence and load-failure paths
- `polisher.rs` — mocks the OpenAI/Anthropic polishing APIs with `mockito`
- Platform modules — construction/smoke tests only
- Three CI jobs in total: Linux `amd64` and `arm64` both run `cargo test --lib`; the Windows job runs tests and builds the NSIS installer on x64, while arm64 only gets a cross-compilation check
