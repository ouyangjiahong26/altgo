# 键盘观察一律走监听器的钩子，不自装钩子

altgo 有两处要“看一次用户的按键”：主页空态的触发键自检与设置页的“按下以设置”。两者一度都自己挂一个 `WH_KEYBOARD_LL` 钩子等一次按键。实测中这两个钩子在 Windows 上装得上、线程也在泵消息，但 altgo 窗口获得焦点时系统在整段等待窗口里一次都没调用它们，把应用里的顺序搬进隔离进程复现则一切正常，说明问题不在观察代码而在钩子链，窗口获得焦点时后装的钩子会被挡在别人的钩子之后收不到事件。监听器自己的钩子在同样条件下一直好用，因为它随流水线在进程早期装上。

决定：键盘观察一律复用监听器挂在管道上的那个钩子。监听器把过滤前的每一个按键（含被当作注入事件忽略的那些）发到一条进程级单槽通道，即原始按键旁路，观察者订阅这条通道。触发键自检与按键捕获都不再自己装钩子，也不为观察停掉流水线。监听器没在跑时“按下以设置”退回临时钩子，那条路径的超时提示写明需要先把焦点切到其他窗口。

## 备选方案

- 继续自装钩子，捕获期间把主窗最小化或失焦：被否决。焦点一挪就可用是实测结论，但窗口挪开就看不到结果，界面要多写一套窗口状态，体验碎。
- 自检期间停流水线再自装钩子：被否决。这正是最初的实现，实测在窗口有焦点时收不到按键，而且停流水线会卸载模型，重启后首次转写要等模型重新加载。
- 只改失败提示文案，让用户自己移开焦点：被否决作为主路径。这是把已知缺陷转嫁给用户，只在监听确实没在跑时作为兜底保留。
- 为观察引入独立的键盘输入库（如 rdev）：被否决。为一个钩子引入新依赖，且拿到的键码语义与现有监听器可能不一致。

## 后果

- 观察期间按键照常录音，按到当前触发键会真的录一段并转写。触发键自检把这个当成便利（顺手得到一次真实转写），按键捕获接受同样的副作用。
- 原始按键旁路是进程级单槽，同一时刻只允许一个观察者，新的订阅会顶掉旧的。
- 按键捕获不再停流水线，省掉一次模型重载，捕获期间流水线状态照常流转。
- Linux 的旁路拿不到注入标记，X11 与 evdev 层面都没有这个信息，只有 Windows 能按注入标记过滤，所以 Linux 上的捕获会把合成键当成物理键。
- 监听没在跑时（配置校验失败导致流水线没起来）只能退回临时钩子，那条路径仍然受焦点影响。
