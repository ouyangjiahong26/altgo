# 本地润色引擎：运行时与模型按需下载，参数固定为实测预设

altgo 的润色此前只有远端一条路，任何离线场景都不可用，而本机实测表明 CPU 上的小模型能把出稿延迟压到可用区间：Qwen3-0.6B Q4_K_M 在 30 条真实转写上热调用中位 273 ms、p95 1.08 s，低于同期云端润色的中位 811 ms，Qwen3-1.7B 的中位是 624 ms。这足以支撑第二种润色引擎。决定：

- `[polisher]` 增加 `backend`（`remote` 与 `local`）。本地档不暴露 API key 与 base URL，也不要求用户填模型名，参数固定为实测预设：温度 0、关闭思考、`max_tokens` 设上限、线程数取物理核数且上限 16、只提供一档（medium 语义）并配一份内置短中文提示词，`system_prompt` 仍可覆盖全部档位。
- 润色运行时（llama.cpp 的 CPU 构建，固定到具体构建号并记录 SHA-256）与本地润色模型（Qwen3-0.6B 与 Qwen3-1.7B 两档 Q4_K_M）都按需下载，不进安装包。实测 Windows x64 的运行时压缩包 19.5 MB，解包后只保留服务器本体与全部动态库，共 30 个文件约 46.7 MiB，二十来个命令行工具不落地。模型走 huggingface.co 与 hf-mirror.com 双源，运行时以 llama.cpp 官方 Release 为主源，另支持配置镜像基址与手动放置文件（识别只看文件是否就位、哈希是否匹配）。
- 润色模型与运行时的清单结构、目录都与转写模型分开，只复用下载内核与 SHA-256 校验。转写侧的 `EngineKind` 不扩展，避免润色语义污染 `resolve_model_dir` 的判断。
- 运行时惰性启动（切到本地档或首次需要润色时拉起），端口动态分配并先试默认端口，空闲 10 分钟后退出，被外部杀掉后下次使用时重启。端口在运行期注入，不再走配置静态值。
- 线程数取物理核数是实测收益最大的一项：同一台机器 16 物理核时生成 100.8 tok/s，22 逻辑线程掉到 60.5 tok/s。

## 备选方案

- 把 llama.cpp 静态链接进主程序。被否决。安装包每份增加 2 到 3 MB 且与“运行时按需下载”的取向冲突，CI 要引入 cmake 与 libclang，win-arm64 交叉编译未验证，且 FFI 崩溃会直接拖垮主进程，而 sidecar 崩溃只死子进程。
- 要求用户自备 Ollama 或 LM Studio，altgo 只负责把请求打到它的端点。被否决作为唯一路径，因为它把可用性押在第三方软件的安装与端口配置上，失败面大。作为逃生门保留在高级区。
- 把运行时放进 `bundle.externalBin`。被否决。四份安装器各增加 19.5 MB 的压缩包或解包后约 46.7 MiB，且每次应用更新都要多下这部分体积。按需下载与转写模型完全同构，发布产物校验、签名与 updater 路径零改动。
- 提供 ERNIE-4.5-0.3B 作为最低配档。被否决。实测它会用“我有什么我可以帮你做的？”接话，30 条语料里 10 条触发保真失败，属于行为错误而不是速度取舍。
- 本地档保留 light、medium、heavy 三档与三份提示词。被否决。0.6B 在长指令下保真失败 8/30、短指令 6/30，分级带来的收益不足以抵消三套提示词与三套阈值的调优成本，用户要分级可切回云端档。

## 后果

- 首次启用本地档要下载约 400 MB（0.6B）或 1.1 GB（1.7B），安装包体积不变，发布产物与更新路径不变。
- 进程生命周期成为新的失效面：端口冲突、被外部杀掉、启动超时、退出后残留。这些要落在平台接缝上并有对应测试，与录音器、按键捕获同类。
- 新增配置字段必须同步 `configs/altgo.toml`，`config/template_guard.rs` 要求两者键集精确相等。
- 常驻内存实测为 0.6B 提交 1.0 GB、1.7B 提交 1.5 GB，空闲退出策略是 8 GB 机器可用的前提。
- 本地档的出稿延迟由录音收尾、转写与本地润色三段构成，不再包含润色的网络往返。
